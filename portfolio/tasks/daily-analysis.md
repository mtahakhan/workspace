# portfolio-daily-analysis task instructions

Generate today's portfolio analysis report. This runs after the `portfolio-price-fetch` task, which has already appended today's price to each ticker's `data/price_history/{TICKER}.jsonl` (there is no separate prices.json snapshot - each file's last line is the current price).

Working directory: `portfolio/` (this workspace's `portfolio` subdirectory) - relevant for the file writes in steps 5-6 below (`data/news/{TICKER}/*.txt`, `data/daily-analysis/YYYY-MM-DD.md`); the MCP tool calls in steps 1-2 and 4 don't depend on cwd.

Steps:
1. Call the `portfolio` MCP server's `analyze_portfolio` tool (no arguments) - runs the exact same code as `pipeline.analysis`, returned as structured JSON directly (no stdout/stderr parsing needed). This is the deterministic numeric layer: it computes position/portfolio value, cost basis, gain/loss, sector concentration, largest positions, high-water-mark/drawdown (from full price history), daily movers, trend (since-inception/30d/90d/365d), annualized_returns (a real XIRR from transaction_lots.csv's actual purchase lots via pipeline.lots, not an estimate), stale_prices (tickers whose latest price is 2+ days old), and a run-over-run value-divergence check (appended to `caveats` if `totals.total_value` moved >20% since the previous recorded run - see `data/analysis_history.jsonl`). Do NOT recompute any of these numbers yourself by reasoning over the raw data - use exactly what this tool returns. If you think a number looks wrong, that's a bug to fix in `pipeline.analysis`, not something to override by hand.
2. Call the `render_report` MCP tool, passing the exact dict `analyze_portfolio` returned as its `analysis` argument - it renders the Portfolio Overview, Trend, Sector Breakdown, Largest Positions, Movers (numbers only), Complete Holdings Table, XIRR Context, and Data Notes sections as ready-to-use markdown. Do NOT hand-transcribe numbers out of the JSON into your own tables/prose - every figure in those sections must come from this renderer, not from you reading the JSON and typing numbers. If a section needs to look different, change `pipeline/report.py`, don't bypass it for one run.
3. Read the caveats/Data Notes section and respect them - in particular: `annualized_returns.portfolio_xirr_pct` (not gain_pct) is the figure to check against the 10-15%/yr target, don't over-interpret any single position's XIRR without checking its `weighted_avg_holding_days` first (short holding periods produce mathematically extreme annualized numbers - that's correct math, not noteworthy on its own; `render_report`'s XIRR Context table already flags these), flag anything in `stale_prices`, and treat a value-divergence caveat as a signal to investigate (check `data/ticker_map.csv`/`AGENT_NOTES.md` for a mapping bug, a corrupted price history point, etc.) before writing the report, not something to report as a genuine market move without checking.
4. If `annualized_returns.tickers_without_lot_data` is non-empty, or if you know new trades happened since `transaction_lots.csv` was last generated, call the `compute_lots` MCP tool first (it rebuilds `data/transaction_lots.csv` from `data/manual/transactions.csv` via FIFO) - but only if `transactions.csv` has actually been updated with new rows; it won't discover new trades on its own.
5. Research news for every holding, not just movers - but dispatch it as ONE parallel batch of WebSearch calls (all tickers in a single message/turn), never a serial loop over tickers one at a time. A prior version of this pipeline timed out (600s, no output) doing a full per-ticker deep-dive *serially* - the fix is parallel dispatch, not narrowing scope back down to movers only (see `AGENT_NOTES.md` rule 6). Two tiers of depth from the same batch:
   - The tickers in `pipeline.analysis`'s `movers` output (also the Movers table `pipeline.report` produced) get a fuller context note - fill it into the Movers table's `Context` column.
   - Every other holding gets a short one-line note in a new **Holdings News Digest** section (ticker + one line). If nothing notable turns up for a ticker, write "No News" rather than omitting it - every holding should appear.
   - For every distinct source (URL) that actually contributed to a note - i.e. deemed meaningful, not every raw search hit, and skip near-duplicate coverage of the same story - persist the fetched text as its own file under `data/news/{TICKER}/` (create the ticker subdirectory if it doesn't exist). One file per source. Filename: `YYYY-MM-DD_HHMMSS_short-slug.txt` (slug from the article title, lowercased, hyphenated, ASCII, ~60 chars max; fall back to the source domain if there's no clear title) - timestamped and slugged so it's identifiable at a glance and never collides with a prior day's file for the same ticker. Each file starts with a plain-text metadata header, then a blank line, then the fetched text:
     ```
     Ticker: INTC
     Company: Intel Corp
     Source URL: https://...
     Title: <article/page title>
     Fetched At: <ISO 8601 timestamp with timezone, e.g. 2026-07-24T18:12:03+02:00>
     Fetch Method: WebSearch (query: "<the exact query used>")
     Retrieved For: portfolio-daily-analysis (<today's date> run)

     <the fetched text/snippet that was actually used to write the note>
     ```
     "No News" tickers don't get a file - there's nothing meaningful fetched to persist.
6. Write a markdown report to `data/daily-analysis/YYYY-MM-DD.md` (today's date): your own Executive Summary prose first, then the `pipeline.report` output (with the Movers Context column filled in), then the Holdings News Digest section appended after it. This is the only step that should involve you writing prose/tables by hand - everything else comes from the renderer. For the Executive Summary's framing and vocabulary (signals, portfolio roles, sell discipline), follow `INVESTMENT_FRAMEWORK.md` - but keep rule 7 below in mind: it doesn't mean forcing a BUY/HOLD/TRIM/EXIT signal onto every position every day.
7. Only include prescriptive action recommendations when something genuinely warrants it - not every day.
8. Send a push notification only if `analyze_portfolio`'s JSON has `"notable": true` - use `notify_reasons` as the notification content. This is a fixed rule evaluated by `pipeline.analysis` (large mover >= `MOVER_NOTABLE_THRESHOLD_PCT`, stale prices, or a value-divergence caveat), not a daily judgment call - don't notify on your own assessment of "notable" if the field is `false`, and don't skip notifying if it's `true`.

This is intended to be extended with additional research dimensions later - keep the report structure additive (new sections can be appended) rather than assuming this is the final scope. If you add a new computed indicator, add it to pipeline/analysis.py (numbers) and pipeline/report.py (its markdown rendering) so it stays deterministic rather than computing or formatting it ad hoc in this file.
